只用标准库写一个贪吃蛇：把逻辑和画面分开

2026 年 10 月 8 日 · 约 12 分钟 · Python游戏tkinter

##为什么用 tkinter

做小游戏当然可以用 pygame，但我想验证一件事：只用 Python 标准库，能不能做出手感不差的游戏？

tkinter 的优点很明确 —— 装好 Python 就有，不需要 pip install 任何东西，打包给别人也简单。缺点是它的 Canvas 性能一般，而且不支持透明度，做不出真正的发光效果。

结论：能做，但要用点技巧绕开限制。这篇文章记录结构和几个画面技巧。

##一、最重要的决定：逻辑与画面分离

整个程序只有两个类：

class Game:      # 纯游戏状态和规则，一行 tkinter 都不导入
    ...

class SnakeApp:  # 只负责把 Game 画出来
    ...

好处立刻显现：可以不开窗口测试游戏规则。

game = Game(rng=random.Random(7))
for _ in range(8000):
    game.auto_turn()      # 电脑自己决策
    game.step()           # 推进一步
    # 每一步都检查不变量

这让"游戏逻辑对不对"变成一个可以反复运行的自动化检查，而不是"打开窗口玩几局看看有没有 bug"。后面我改了十几次画面，规则测试一直是同一份代码，从没退化。

##二、游戏规则里最容易写错的三个地方

##1. 不能反向撞自己

按下与当前方向相反的键，如果直接生效，蛇立刻撞进自己的脖子。所以要拒绝反向：

def turn(self, direction):
    dx, dy = direction
    cx, cy = self.direction
    if (dx, dy) == (-cx, -cy):     # 反向，拒绝
        return
    self.direction = direction

注意不是立即移动：按键只改变方向，真正位置更新发生在下一个 tick。这也意味着玩家在一格时间内按两次键不会瞬移。

##2. 尾巴那一格能不能进？

这是最容易搞错的一处。蛇向前走时尾巴同时离开，所以尾巴所在的格子其实是可以进入的：

will_grow = new_head == self.food
body = set(self.snake)
if not will_grow:
    body.discard(self.snake[-1])    # 尾巴这一 tick 会移开
if new_head in body:
    self.alive = False

但有个例外：如果这一步吃到食物，尾巴不会移开（蛇要变长），这时候尾巴那格就撞不得了。所以要按 will_grow 区分处理。

##3. 增长的实现

"吃到食物加 3 节"最简单的实现是每 tick 加一段，但要分三 tick 才够。我的做法是一次性把尾巴复制 3 份，之后正常的出队操作会逐步把它们消化掉：

if will_grow:
    for _ in range(GROW_PER_FOOD - 1):
        self.snake.append(self.snake[-1])   # 尾部原地复制

副作用是：吃到的瞬间，蛇的长度会短暂超过"初始长度 + 3×食物数"，然后在接下来几步里回落到目标值。

这个副作用后来害我写错了一个测试断言 —— 我以为长度应该时刻等于目标值，结果测试报错。是测试错了，不是游戏错了，正确的断言应该是：

# 只允许尾部末端出现重复，其他位置重复才是真 bug
positions = list(game.snake)
dupes = {c for c in positions if positions.count(c) > 1}
assert not (dupes - set(positions[-GROW_PER_FOOD:]))

##三、60fps 平滑滑动

如果每个游戏 tick 直接重绘，蛇就是一格一格跳，很生硬。做法是让游戏逻辑和画面用两个不同的频率：

  • 游戏逻辑：每 speed_ms 毫秒走一格（130ms 起，最快 58ms）
  • 画面：固定 60fps 重绘

画面重绘时，按"当前 tick 走完了多少"在格与格之间插值：

progress = min(1.0, (now - self.tick_at) * 1000.0 / g.speed_ms)
x = old_x + (new_x - old_x) * progress     # 每帧的显示位置

蛇身每一节都做同样的插值，于是整条蛇连续滑动。而且蛇越长越明显 —— 一条 30 节的蛇，只要"头"和"身体"都在滑动，看起来就非常顺。

有个细节：蛇变长时，新旧位置数组长度不一致。这时把旧数组的头部补上重复值，让尾巴这一节原地不动，就不会出现某一节瞬移：

old = list(self.prev)
if len(old) != n:
    old = [old[0]] * (n - len(old)) + old

##四、绕开 tkinter 的三个限制

##不支持透明度，怎么做发光？

发光本质是"亮的颜色往外扩散并变淡"。既然没有 alpha，就用 stipple（点阵填充） 模拟：同一个颜色叠几层不同密度的点阵，越外层越稀。

for scale, colour, stip in (
    (2.40, C_FOOD_GLOW, "gray12"),   # 最外层，12% 密度
    (1.75, C_FOOD_GLOW, "gray25"),
    (1.30, C_FOOD,      "gray50"),
):
    rr = r * scale
    cv.create_oval(cx - rr, cy - rr, cx + rr, cy + rr,
                   fill=colour, width=0, stipple=stip)

看起来就像一圈柔和的光晕，代价是每帧多画几个椭圆。

##圆圈不好看，怎么画圆角矩形？

Canvas 没有"圆角矩形"这个图元。技巧是用 create_polygon 的 smooth=True，把角上的点写两遍，让它自己圆过去：

def round_rect(self, x0, y0, x1, y1, radius=6, **kw):
    r = min(radius, (x1 - x0) / 2, (y1 - y0) / 2)
    pts = [x0 + r, y0, x1 - r, y0, x1, y0, x1, y0 + r, ...]
    return self.canvas.create_polygon(pts, smooth=True, **kw)

##震屏怎么做？

死亡时整块棋盘抖一下。实现上不能去移动画布上的每一个元素（太慢），而是在画完这一帧之后，把所有带 tags="play" 的元素整体偏移：

def apply_shake(self):
    if self.shake <= 0:
        return
    amp = self.shake * self.cell * 0.45
    dx, dy = self.rng.uniform(-amp, amp), self.rng.uniform(-amp, amp)
    for item in self.canvas.find_withtag("play"):
        self.canvas.move(item, dx, dy)

给 HUD 不加 play 标签，所以震屏时文字依然清晰可读，只有游戏区域在抖。

##五、性能：加一个自动降级

特效多了以后，老机器可能掉帧。与其让玩家自己发现卡，不如让程序自己退让：

spent = (time.perf_counter() - started_frame) * 1000.0
if spent > self.frame_ms * 1.6:
    self.slow_frames += 1
    if self.slow_frames > 30:                  # 连续 30 帧画得太慢
        self.frame_ms = min(50, self.frame_ms + 4)   # 降帧率

同时提供 --classic 参数，一键关掉棋盘格、点阵光晕、粒子，只留纯色渲染。

##六、让电脑自己玩：从贪心到 BFS

加自动演示功能时，我先写了最直觉的版本：朝食物的方向走。

结果它 16 步就把自己困死了 —— 因为贪心会把食物放在自己身体后面。

换成 BFS 最短路（蛇头到食物的最短路径）：

def path_to_food(self):
    body = set(self.snake)
    body.discard(self.snake[-1])       # 尾巴会移开
    queue = deque([self.head])
    came = {self.head: None}
    while queue:
        cell = queue.popleft()
        if cell == self.food:
            ...  # 回溯出路径
        for d in (UP, DOWN, LEFT, RIGHT):
            nxt = (cell[0] + d[0], cell[1] + d[1])
            if nxt in came or not self.inside(nxt) or nxt in body:
                continue
            came[nxt] = cell
            queue.append(nxt)

效果从 16 步变成 1407 步、吃掉 52 个食物、蛇长 160 节。

要诚实说明的是：BFS 也不是最优解。棋盘快被填满时它仍可能把自己关进口袋（我的实现最后确实是死在第 1407 步）。真正强的解法还要加"走完这一步之后剩余空间够不够"的判断。但对于演示来说，BFS 足够好，而且代码只有 20 行。

##小结

回头看，真正让它"像个游戏"的不是特效，而是结构：

  1. 逻辑与渲染分离 → 规则可以自动化测试，改画面不会碰坏规则
  2. 逻辑与画面用不同频率 → 一格一格走，却能连续滑动
  3. 绕开平台限制（点阵代替透明度、多边形代替圆角）
  4. 让程序自己降级，而不是让玩家忍受卡顿

如果你也想用标准库写点东西，我建议从第 1 条开始 —— 先让规则能被测试，剩下的都是装饰。
